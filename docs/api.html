caus API

A compact, offline reference for the caus platform HTTP API: people, talks, competitions, teams, accounts and Google-backed administration.

01

Quick start

Every route is relative to BASE_URL. Public reads need no credentials. Signed-in and admin routes use the browser session cookie created by the Google OAuth flow.

BASE_URL=http://localhost:8080
PUBLIC_URL=http://localhost:8080
curl -i "$BASE_URL/api/healthz"
  • JSON API. Success bodies are JSON except the iCalendar feed and 204 responses. Errors use a single { "error": { "code", "message" } } envelope.
  • Methods. 33 method and path combinations are documented. HEAD is accepted on every GET. OPTIONS is only meaningful as a CORS preflight.
  • Authentication. Google OIDC with PKCE S256, state and nonce. Scopes are openid email profile. There is no password login, bearer token or JWT endpoint.
  • Not available. There is no POST /api/people and no refresh token.

Example values. BASE_URL=http://localhost:8080 and PUBLIC_URL=http://localhost:8080 are illustrative. A local frontend's PUBLIC_URL may be another localhost port and must match the actual configured value or proxy. Replace illustrative UUIDs and cookie placeholders with real values.

02

Authentication and OAuth

Login is Google OIDC authorization-code flow with PKCE S256, a random state and a nonce. Requested scopes are openid email profile. The backend validates the Google ID token, including issuer, audience, signature, nonce and verified email, then stores only the session token hash.

Flow

  1. Configure a Google Web OAuth client with the exact redirect URI PUBLIC_URL + /api/auth/google/callback and the authorized frontend origin.
  2. Start a top-level browser navigation to window.location.assign('/api/auth/google/login?return_to=' + encodeURIComponent('/')). The login route sets the OAuth flow cookie (__Host-caus_oauth over HTTPS, caus_oauth on HTTP localhost) and redirects to Google.
  3. Google redirects to the callback with provider-managed code and state. The callback checks the cookie and state, exchanges the code, validates identity and sets the session cookie (__Host-caus_session over HTTPS, caus_session on HTTP localhost).
  4. Call fetch('/api/me', { credentials: 'include' }) to read the account and role. Roles are read per request.

Identity checks

  • ID token. The Google ID token must validate its issuer, audience, signature, expiry and nonce. A token that fails any of these returns 401 invalid_identity.
  • Verified email. The ID token email must be verified by Google.
  • Names. A nonblank first name is required locally; the last name may be an empty string because some Google accounts have no family name, so a missing family name no longer fails sign-in. Names are copied from Google only at the first sign-in; later logins never refresh stored names. A blank or missing first name fails with 422 invalid_identity.
  • Email collisions. An email already bound to a different Google identity returns 409 identity_conflict. Accounts are never merged by email silently.

The browser sends one session cookie only. The Secure attribute follows the configured PUBLIC_URL scheme, not the scheme of the incoming request. Over HTTPS only the __Host--prefixed names are issued and read, so upgrading to HTTPS requires users to log in again. Missing, empty, duplicate, malformed or expired sessions return 401 unauthenticated.

Roles, origin and browser rules

  • Access badges. Public needs nothing, Signed in accepts a member or admin, and Admin requires an admin.
  • Admin access. Authorization reads only the stored account role: role must be admin. Any admin can grant admin to any existing account with PATCH /api/admin/users/{id}, including an email that is not on ADMIN_EMAILS. ADMIN_EMAILS is optional and applies only at login as a one-time bootstrap: the first login with an allowlisted, authoritative Google email (@gmail.com or a Workspace hosted domain) consumes a hashed-email marker and becomes admin, after which the stored role alone authorizes requests. A nonauthoritative allowlisted email signs in as a member and can be granted admin later by an existing admin. Removing an allowlist entry demotes nobody, and this bootstrap rule affects only future first promotions, not existing roles. The last remaining admin cannot be demoted and cannot delete their account; both requests answer 409 conflict.
  • Writes. Every POST, PATCH and DELETE requires an Origin header exactly equal to the canonical configured PUBLIC_URL. Otherwise the response is 403 origin_denied.
  • HttpOnly sessions. JavaScript cannot read the session cookie or token. Normal clients log in with top-level browser navigation. The caus_session=YOUR_SESSION_COOKIE placeholder in CLI examples is for manual use only.
  • Logout. Send fetch('/api/auth/logout', { method: 'POST', credentials: 'include' }). The browser sets Origin automatically. Never set the forbidden Cookie header in browser fetch.
  • Separate dev frontend. Set the API origin explicitly, set PUBLIC_URL to the frontend origin, and proxy the /api callback. CORS allowance alone does not authorize a write Origin or defeat SameSite cookie rules; a same-origin reverse proxy is recommended.

The login and callback examples do not complete Google login with curl. Login is a 302 to Google. Callback code and state values are provider-managed illustrative placeholders.

03

Conventions

  • Envelope. Successful reads return either a bare object, a paginated { "data": [...], "pagination": { "limit", "offset", "has_more" } }, or the documented detail shape. 204 responses have no body.
  • Pagination. limit is 1..100 and defaults to 20. offset is 0 or greater and defaults to 0. Duplicate or invalid values return 400 invalid_pagination.
  • Event dates. Exactly YYYY-MM-DDTHH:MM:SS: no Z suffix, no UTC offset and no fractional seconds. The value is read as a Europe/Madrid wall clock, and invalid dates or local times that do not exist in Europe/Madrid are rejected. created_at and updated_at are UTC RFC3339 timestamps.
  • Durations. Whole seconds from 1 through 9223372036. The computed end date must be representable in years 1..9999.
  • HEAD. Accepted on every documented GET with the same headers and status as the GET response. There is no separate HEAD endpoint entry.

05

Requests

JSON request models and validation rules. Bodies are required only on the methods that document them.

Global JSON decoding

  • Content-Type: application/json is required; parameters are allowed. Missing or unsupported media types return 415 unsupported_media_type.
  • The body is limited to 64 KiB. Larger bodies return 413 request_too_large.
  • The body must be one non-null JSON object. Unknown fields, trailing extra JSON, empty bodies or the wrong structure return 400 invalid_body.
  • Valid JSON with wrong types, null in a nonnullable field, or missing required fields returns 422 validation_failed with an error.fields map.
  • An empty {} patch returns 422 with error.fields.patch.
  • String values are stored with surrounding whitespace removed.
  • Talk title and location, competition name and location, and team name accept at most 200 characters and answer 422 validation_failed otherwise.

08

CORS

  • Allowed origins. Only the exact configured PUBLIC_URL origin. An HTTP localhost origin is allowed only when it is itself the configured PUBLIC_URL.
  • Credentials. Access-Control-Allow-Credentials: true. The allowed origin is echoed; Vary: Origin is set.
  • Preflight. OPTIONS is meaningful only as a preflight with Access-Control-Request-Method. Allowed request headers are Accept and Content-Type only. A valid preflight returns 204 with Access-Control-Max-Age: 600.
  • Denials. A disallowed origin returns 403 cors_origin_denied. A disallowed requested header returns 400 cors_headers_denied.
  • Exposed headers. Retry-After and X-Request-ID.
  • Not a blanket method. There is no anonymous catch-all OPTIONS behavior; only preflight is supported.

09

Rate limits

  • 60 requests per 60 seconds per client, in one shared bucket. The limit applies to every route under /api/auth/ and to every request whose method is not GET or HEAD; other GET and HEAD requests are never rate limited.
  • IPv6 clients are counted per /64 network and IPv4 clients per address.
  • Exceeding the limit returns 429 rate_limited with Retry-After as integer seconds.
  • CORS preflight is handled before the limiter.
  • X-Forwarded-For is trusted only from loopback peers, and only its rightmost token is used. Forwarded headers from non-loopback peers are ignored entirely.
  • The server binds 127.0.0.1:PORT, default port 8080.
